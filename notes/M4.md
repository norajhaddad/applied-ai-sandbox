# M4 — Reading and Verifying Output

## Bug hunt #1 — SQL injection
- Bug: The query is built with an f-string that drops the raw user input q straight into the SQL, so it is a classic SQL injection — a value like ' OR 1=1 -- or '; DROP TABLE notes; -- changes what the query does and lets an attacker read or destroy data.
- Why Claude wrote it: An f-string assembling a SQL string reads as clean, obvious code and mirrors countless tutorial snippets, and without the context that this is SQLAlchemy (which expects a text() construct with bound parameters) string interpolation looks like the natural way to insert the search term.
- Fix: Use a parameterized query — wrap the SQL in sqlalchemy.text() with a named placeholder (LIKE :pattern) and pass {"pattern": f"%{q}%"} as bound parameters, so the database treats q as data and never as executable SQL.

## Bug hunt #2 — hallucinated package
- Bug: flask_simpleauth is not a real package — pip show flask_simpleauth reports "Package(s) not found", so the import raises ModuleNotFoundError and the app cannot start; it is a hallucinated dependency that only looks plausible.
- Why Claude wrote it: The name follows the very common Flask-extension naming convention (flask_login, flask_sqlalchemy, flask_wtf), and LoginManager and login_required are genuine Flask-Login APIs, so a plausible-sounding but invented module name got stitched onto real symbols — idiomatic-looking without ever being checked against PyPI.
- Fix: Use the real library, Flask-Login — run pip install Flask-Login and import from flask_login instead: from flask_login import LoginManager, login_required. The LoginManager, init_app, and login_required usage is otherwise correct.

## Bug hunt #3 — edge case
- Bug: average_rating([]) raises ZeroDivisionError: division by zero, because len(ratings) is 0 and sum([]) / 0 is undefined; the empty-list case is never handled, and Claude's own test only covered a non-empty list so it passed anyway.
- Why Claude wrote it: sum/len is the textbook definition of an average and the self-written test exercised only a typical non-empty input, so the empty-collection edge case — a normal real-world state, like a note or product with no ratings yet — was never considered.
- Fix: Guard the empty case before dividing, e.g. return sum(ratings) / len(ratings) if ratings else 0.0 (or return None / raise a clear ValueError if "no ratings" should be distinguished from an average of zero).

## Bug hunt #4 — hardcoded secret
- Bug: The OpenAI API key is hardcoded directly in the source, so it gets committed to git history and exposed to anyone who can read the repo; a leaked key can be used to run up charges on the account, and it stays in history even if you later delete the line.
- Why Claude wrote it: Inlining the literal key makes the snippet self-contained and runnable as-is, which looks convenient in an isolated example; without the context of version control and deployment, a hardcoded key reads like the simplest way to authenticate.
- Fix: Never hardcode secrets — read the key from an environment variable, e.g. import os; client = openai.OpenAI(api_key=os.environ["OPENAI_API_KEY"]) (the SDK also picks up OPENAI_API_KEY on its own), and keep it in a gitignored .env loaded with python-dotenv for local dev. Critically, rotate/revoke the exposed key right away, since once it has been committed it must be treated as compromised.

## Near-miss reflection
- In the bad-context experiment, Claude built what looked like a complete login system — login and logout routes, a seeded user, a session, a login_required decorator, and UI state — and reported that all ten of its own tests passed. On the surface it looked done, and it would have been easy to accept the green test run and move on. What made me stop was reading what the code actually did: the gate was never attached to any route, so being logged in changed nothing, and the tests passed only because Claude wrote them to cover the parts it built, not the goal I actually wanted. A verification habit — asking "what does this feature actually protect, and does it meet the real requirement rather than just Claude's self-written tests?" — would have surfaced that gap immediately. The lesson is that green tests prove the code does what the test says, not what I meant, so I have to check against the goal myself.
