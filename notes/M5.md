# M5 — Decomposition

## 5-step framework

1. Define done — describe the concrete end state (a user can do X and see Y; existing tests still pass), not "the feature works."
2. List the components — the files, routes, tables, templates, and tests that must exist.
3. Order by dependency — what has to exist before what (model before route, route before template).
4. Define each step in isolation — input (what state is the repo in?), action (what does Claude do?), output (what changed and what verifies it?).
5. Insert checkpoints — between steps, one sentence on how you will manually verify before moving on. Aim for 6 to 10 steps.

## Reflection — where I redirected

The code plans were right on the first try (one-to-three-line diffs); what was actually
off was the brief's baseline — Task 1's "all existing tests still pass" and Task 3's
"preserve tags the same way title and body already are" both assumed a Task 01 validation
that was never on these branches, and Claude had to flag both rather than me catching them.

Task 2's brief borrowed part of the lesson — it carried forward Task 1's "this is unrelated
to the pre-existing test_task_01/02 failures" caveat — but missed the bigger one, that the
whole chain silently assumes Task 01 exists, which is exactly what tripped Task 3.

If I redid the decomposition I'd make "confirm or merge the Task 01 baseline" an explicit
step 0, since most of the real friction came from acceptance criteria depending on a
prerequisite that wasn't on the branch (and, secondarily, from splitting the notes across
cohort-notes and the feature branch, which kept making M3/M4 look deleted).
