# M7

Feature pick: note pinning — each note gets a pinned flag (defaulting to false) and a toggle button, and pinned notes float to the top of the list view.

## Plan from chat

Note pinning — design

1. Data-model changes
- Add a single field to the note dict: pinned: bool, default False.
- That is the whole change. No pinned_at timestamp, no manual pin-order field, no separate pinned_notes list — those are over-engineering for an in-memory practice app and would have to be torn out later anyway.

2. Route changes
- New: POST /notes/<idx>/pin — toggles pinned on the note at that index. Follows the existing per-note action pattern (same shape as the delete route). One toggle endpoint, not separate pin/unpin routes.
- Modified: GET / — before passing notes to home.html, return a stably sorted view: pinned first, unpinned after, each group in its original insertion order. A stable sort with key lambda n: not n.get("pinned", False) does this in one line. Do not mutate app.notes itself — sort a view for rendering only, so insertion order is preserved as the source of truth.
- POST /notes/new is unchanged. New notes are unpinned by default, and the .get fallback (see edge cases) means we don't even strictly need to set the key on creation — but setting "pinned": False explicitly is fine and slightly clearer.

3. UI changes
- Each note in home.html gets a pin control — a small button or icon inside a form that POSTs to /notes/<idx>/pin. Label flips between "Pin" and "Unpin" based on the current state.
- Pinned notes appear at the top of the same list with a small visual marker (a pin icon or a "Pinned" tag) so the reordering is explained. No separate "Pinned" section header — one list, sorted.
- No drag handles, no reorder arrows, no per-pin priority. The user pins or unpins; that's the whole interaction.

4. Edge cases
- Notes missing the pinned key must default to False. Always read with note.get("pinned", False) — in the sort key and in the template. Never index with note["pinned"]. This is the safety net that keeps notes created before the feature (and any future code path that forgets to set the key) from raising KeyError.
- Invalid <idx> on the pin route: 404, matching whatever the delete route already does — don't invent a new error pattern.
- Toggle semantics: pinning an already-pinned note unpins it. Single endpoint, no separate states to reconcile.
- Empty list: nothing to sort; view renders as before.

Explicitly out of scope (do not build)
- Drag-to-reorder. Manual pin ordering (pin slot 1, 2, 3...). pinned_at timestamps or any "most recently pinned first" logic. A separate app.pinned_notes list or any second data structure. Separate /pin and /unpin routes. A migration pass over existing notes to backfill the key — the .get default makes it unnecessary.
- If a follow-up ticket genuinely needs one of these, revisit then. For now, the simplest thing that works is: one bool, one toggle route, one stable sort, one .get default.

## Execute in Claude Code

Branch: m7-note-pinning (off main, not merged). Implemented exactly as planned —
"pinned": False on new notes, a stable pinned-first sort in home(), POST
/notes/<idx>/pin toggle, a pin/unpin button and a Pinned badge in home.html, and
five new tests in tests/test_m7_pinning.py (all pass; the 6 remaining suite
failures are pre-existing unimplemented Task 01 / Task 02 tests, not regressions).

What Claude Code flagged that the chat plan didn't anticipate: the plan said to
render a stably sorted view while keeping POST /notes/<idx>/pin keyed by index,
but those two steps don't compose. Once the list is sorted for display, a note's
position in the rendered loop no longer matches its index in app.notes, so a pin
button built from the loop position would toggle the wrong note. The fix was to
enumerate(app.notes) BEFORE sorting and carry each note's original index into the
template, so the button always posts the correct app.notes index. (Secondary: the
plan said to return 404 "matching whatever the delete route already does," but the
delete route doesn't exist yet — it's a Task 02 stub — so there was no existing
pattern to match, and I added an explicit bounds-check abort(404).)

## Review in chat

Pasted the diff into chat for review. The headline piece of feedback: index-based
identity is a time bomb. The pin route addressed notes by list position
(/notes/<idx>/pin), but the header comment says TASK 02 will add a delete route —
the moment that lands, indices shift and a pin click hits the wrong note (or a
404). The reviewer said to give notes a stable id now, before delete makes the bug
user-visible, and noted most of the rest of the "risky" list collapses once that
is fixed.

Acted on (commit 9fa6657 on m7-note-pinning):
- Added a monotonic app.next_note_id counter; new notes get a stable "id".
- The pin route is now /notes/<int:note_id>/pin and looks the note up by id
  (next(... if n.get("id") == note_id ...)), not by position — correct even after
  the list is reordered or a note is deleted.
- home() no longer needs the enumerate/index trick; it just stable-sorts the
  dicts, and the template addresses each note by note.id. Guarded the pin form
  with {% if note.id is defined %} so notes lacking an id don't crash rendering.
- Added test_pin_targets_by_id_not_position (reverses the list, then pins by id
  and asserts only the intended note is pinned) to lock the fix in. 6/6 pinning
  tests pass; no new suite failures.

Logged but not acted on this round (would be follow-ups): CSRF token on the
state-changing POST, a threading.Lock around app.notes mutations, friendlier
flash+redirect instead of abort(404), and aria-pressed / aria-hidden for the
toggle's accessibility. (The accessibility one was done later — see Parallel
sessions.)

## Parallel sessions

Second task: implement TASK 02 — add a POST /notes/<idx>/delete route plus a
per-note Delete button in home.html so tests/test_task_02.py passes. Done in the

Worktree path: ../sandbox-task-b (/Users/solo/Projects/sandbox-task-b), branch
task-b, created with: git worktree add ../sandbox-task-b -b task-b main. The
first worktree stayed in the main sandbox dir on m7-note-pinning, where session 1
did the accessibility polish (aria-pressed + aria-hidden) in checkpoints.

Did it actually parallelize? Partly, and honestly the win was modest. There was
real overlap — while session 1 sat at a checkpoint waiting on me, the task-b
session was busy for about two minutes. But two things kept the benefit small.
First, the tasks were small, so session 1 finished quickly and there wasn't a
long window to fill. Second, a big chunk of task-b's "busy" time was not feature
work at all: the fresh worktree had no .venv, so that session burned time
rediscovering the setup (pytest not found, then python/python3 missing, then
creating a venv from requirements.txt) before it could run a single test. So I
got genuine overlap, but mostly while task-b was fighting its environment rather
than building the feature, and with tasks this small it was still tempting to
watch one and let the other idle.

Takeaway: parallelism pays off more when the second task is big enough to keep
its session busy, and when the new worktree is pre-provisioned (copy or create
the .venv first) so the agent doesn't spend its "parallel" time on setup.

## Workflow retro

The four lanes. I planned the feature in chat (claude.ai) — a one-page design of
the data model, routes, UI, and edge cases. I built it in Claude Code: a branch,
the pinned flag, the pinned-first sort, the pin route, and tests. I reviewed it
by pasting the diff back into chat. The polish lane was meant to be Copilot
inline, but it wouldn't load, so Claude Code stood in for the rename and docstring
tweaks.

Where one tool caught what another missed. Two moments. While building, Claude
Code noticed the plan's quiet contradiction: it wanted a sorted display view and
an index-keyed route, but once the list is sorted the loop position no longer
matches the list index, so the button would toggle the wrong note. Then the chat
review caught the deeper one nobody flagged — index-based identity is a time bomb
that breaks the moment the delete route lands. The plan, the build, and I all
missed it; a fresh set of eyes on just the diff found it.

What I'd reroute. Get the review before building, not after. The index-identity
fix was a refactor I could have avoided by reviewing the plan first, or asking
Claude Code to red-team its own plan before writing code. I'd also pre-provision
the second worktree's venv so the parallel session wasn't half-spent on setup.

Where I spent the most conductor time. Routing and reviewing — deciding which
feedback to act on, and toggling between sessions and branches. The review
decision (acting on the headline flag, not the easy nits) was the right place to
spend it; the git and branch juggling was overhead I'd like to cut.
